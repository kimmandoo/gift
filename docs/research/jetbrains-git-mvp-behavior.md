# JetBrains Git MVP behavior ledger

This is the product's primary behavior ledger for black-box reverse engineering
of the user-visible Git GUI system in JetBrains IDEs. It records the workflow
and information hierarchy that gift intends to reproduce, using neutral
implementation names and independently verifiable Git state.

This clean-room ledger contains no proprietary captures, source, binaries,
assets, or implementation details. An observation describes only the starting
state, user action, visible result, and corresponding system-Git result. Later
authorized observations append versioned notes to the relevant scenario; an
uncertain observation stays marked as a hypothesis until verified.

The matching visual target is defined in
`docs/superpowers/specs/2026-09-02-jetbrains-git-gui-pixel-ui-design.md`: a
minimal 2D pixel-game interface with desktop Git GUI information density.

| STATUS-01 | approved design | A repository contains tracked and/or changed files. | See the repository's current working state. | The UI identifies changed, staged, untracked, and conflicted files and their relevant state. | `git status --porcelain=v2 -z --branch` produces the represented branch and file facets. |
| DIFF-01 | approved design | A selected file has staged or unstaged content changes. | Inspect the selected change. | The UI lazily shows a readable, line-numbered unified diff for the selected file; staged and working-tree scopes can be switched, while binary and empty output have explicit states. | `git diff --find-renames --unified=3` or `git diff --cached --find-renames --unified=3`, with the selected path after `--`, produces the represented change. |
| STAGE-01 | approved design | A working-tree change is available and not yet staged. | Add the selected change to the next commit. | The UI disables the action while the mutation runs, then moves or marks the selected change as staged and keeps it selected. | `git add -- <path>` adds the selected path to the index; the returned `git status --porcelain=v2 -z --branch` snapshot shows its staged facet. |
| DISCARD-01 | approved design | A tracked file has an unstaged working-tree change. | Revert the selected working-tree change. | The UI requests a fresh confirmation, disables the destructive action while running, preserves staged content, and removes the selected change from the changed-files view when no facet remains. | `git restore --worktree -- <path>` runs only after the repository/path/status/diff preview remains fresh; the returned `git status --porcelain=v2 -z --branch` snapshot has no discarded unstaged facet. |
| COMMIT-01 | approved design | The index has staged changes and the user has supplied a non-empty commit message. | Create a local commit. | The commit editor accepts Unicode text, disables itself while Git runs, reports the new commit ID on success, returns the staged changes to a clean state, and explains when a commit hook rejects the operation. | The backend sends the message as UTF-8 stdin to `git commit --file=-`; a new `HEAD` commit contains the staged tree and message, and the returned status has no remaining staged changes. |
| LOG-01 | approved design | The repository has one or more commits. | Browse recent history. | The UI lists commits in stable topological order with author/date/subject metadata, shows merge context, and loads the next bounded page on request. | `git for-each-ref` plus `git rev-parse HEAD` captures local/remote/tag tips, then `git log --topo-order <snapshot tips> --format=... --max-count=<page+1> --skip=<offset>` supplies the represented commit ordering, parents, metadata, and page boundary. |
| BRANCH-01 | approved design | The repository has a current branch and may have additional local branches. | View, create, or switch a local branch. | The popup identifies the current branch, validates a new name, reports dirty-worktree failures, and reflects a successful branch creation or selection. | `git for-each-ref` supplies local refs; `git switch --create <name>` or `git switch <name>` updates `HEAD`, and the returned status identifies the selected branch. |
| REMOTE-01 | approved design | The repository has a configured remote and a local branch that can synchronize. | Fetch, pull, or push through the selected remote. | The UI shows the selected remote, indeterminate progress, cancellation, authentication/network/non-fast-forward/conflict feedback, and the resulting local/remote relationship. | `git remote --verbose` supplies the configured remote; `git fetch --prune <remote>`, `git pull --ff-only <remote> <branch>`, or `git push <remote> <branch>` updates refs according to the operation result, unless the cancellation token stops the process. |
| WORKSPACE-01 | approved design | The app has previously opened several canonical repository roots. | Resume work after restarting gift. | The workspace restores the saved tab order and last active tab; an unavailable path stays visible with a recoverable explanation. | Each saved path is independently validated by the backend and receives a new session-local opaque repository ID; persisted data never contains those IDs. |
| WORKSPACE-02 | approved design | One or more repository tabs are open. | Open, close, reorder, or switch repository tabs. | The active tab is visibly selected, tab operations preserve the remaining order, duplicate canonical roots are not added, and the last active path is persisted. | Each tab's Git requests use only its own validated root and opaque repository ID. |
| WORKSPACE-03 | approved design | A repository mutation is running while another repository tab is selected. | Continue inspecting another repository without cross-talk. | The selected tab remains responsive; progress, errors, selection, and refresh results remain attached to the originating tab. | The mutation queue and status snapshot are scoped to the originating repository ID and cannot update another repository. |
| PARTIAL-01 | approved design | A text file has two or more independent hunks in the working-tree diff. | Stage only the selected hunk. | The selected hunk is staged, unselected hunks remain unstaged, and the diff labels the operation as working-tree staging. | A machine-generated patch is sent to `git apply --cached`; the patch contains the selected hunk and enough context to apply safely. |
| PARTIAL-02 | approved design | A hunk contains additions, deletions, and possibly a no-newline marker. | Stage or unstage selected lines. | Line checkboxes support a selected range; only selected additions/deletions move to the target facet, while unselected lines remain in their original facet. | The backend derives a bounded patch from parsed diff lines; UI text is never accepted as arbitrary patch input. |
| PARTIAL-03 | approved design | A diff was selected and the file changed before the mutation. | Apply the previous selection. | The operation is rejected with a stale-diff explanation and no index change. | The selection's repository ID, path, scope, and content hash must match a fresh diff before `git apply` runs. |
| PARTIAL-04 | approved design | The selected path is binary, rename-only, or the generated patch no longer applies. | Attempt partial staging. | The UI explains that partial staging is unavailable or failed and keeps the current selection recoverable. | Binary/rename-only patches are not treated as text hunks; Git patch failure is typed and the mutation queue remains consistent. |
| COMMIT-02 | approved design | The index has staged changes and Git identity may be configured locally, globally, or not at all. | Review identity before committing. | The commit options identify the effective name/email, explain whether values come from local or global configuration, and give exact commands for missing values before mutation. | `git config --local/--global --get user.name` and `user.email` provide the preflight inputs; no commit process starts when an effective identity is incomplete. |
| COMMIT-03 | approved design | A repository has staged changes and may have a commit template. | Choose amend, sign-off, cleanup, template, or author options. | A collapsible options panel describes amend's history replacement, loads the configured template into the editor, can reset it, and shows the selected cleanup/author settings. | The backend sends typed options as `git commit --amend`, `--signoff`, `--cleanup=<mode>`, and `--author=<name> <email>` arguments while the message remains UTF-8 stdin. |
| COMMIT-04 | approved design | A commit command, hook, signing helper, or post-commit refresh can fail. | Understand whether retrying is safe. | Hook/signing diagnostics remain redacted; the UI explicitly says whether history was unchanged or a commit was created but status refresh failed. | The backend compares `HEAD` around the mutation and tags failures as commit-not-created or commit-created-but-refresh-failed. |
| HIST-01 | approved design | Refs may advance while a history list is open. | Load the next page without losing or repeating rows. | The list keeps the original result set and graph-lane continuity even after a new commit or ref movement. | The first page captures bounded ref tips; later pages use the same immutable snapshot cursor and query key. |
| HIST-02 | approved design | A repository contains commits with varied metadata and paths. | Narrow history by text, author, date, ref, or path. | Filter controls are bounded, cancellable by a new request, and show an empty result without stale rows. | Git receives validated argv filters and a path after `--`; the result remains paginated against one snapshot. |
| HIST-03 | approved design | A selected commit may be a root, merge, or contain deleted/binary files. | Inspect what changed in the commit. | Changed files load lazily; selecting a file shows a bounded diff or an explicit binary/empty state. | `git diff-tree --root --name-status -z` supplies file changes and a bounded commit diff supplies parsed text/binary states. |
| HIST-04 | approved design | Two commit or file selections are requested before the first detail request returns. | Continue inspecting the newest selection. | Older responses cannot replace the selected commit's files or diff, and loading/error state belongs to the newest request. | Controller request generations bind each response to the selected OID and path before publishing it. |
| HIST-05 | approved design | A commit has refs and parents that may not be visible on the current page. | Navigate history and copy an exact OID. | Refs, copyable OIDs, clickable parent navigation, and keyboard up/down traversal remain available without breaking lane continuity. | Ref tips are attached to the snapshot; parent lookup is validated by full OID and returns a bounded commit record. |
| BRANCH-02 | approved design | A local branch can be renamed or deleted, including an intentionally force-deleted unmerged branch. | Review and apply a ref-only branch change. | A preview identifies source/target and whether data may be lost; invalid names and stale confirmations are typed, and reachable commits remain recoverable. | `git check-ref-format --branch <name>` validates names; `git branch --rename`, `git branch --delete`, or `git branch --delete --force` runs only for the preview's current repository state. |
| BRANCH-03 | approved design | The current branch and a source branch/commit may be fast-forwardable, divergent, or conflicting. | Merge, rebase, or cherry-pick a reviewed change. | The preview shows source, target, ahead/behind, merge-base, dirty/detached/in-progress preflight, and the exact recovery controls after a conflict. | Git runs only against the reviewed target; start, continue, skip, and abort are separate commands and never inferred from a generic failure. |
| BRANCH-04 | approved design | An advanced branch operation is running or its preview was created before refs/worktree state changed. | Cancel or retry safely. | Cancellation leaves an explicit cancelled state; a stale preview is rejected before mutation and the user can create a fresh preview. | A short-lived token is bound to the repository, request, and status/ref fingerprint; no reachable commit is removed by cancellation or abort. |
| CONFLICT-01 | approved design | A merge, rebase, or cherry-pick has unmerged index entries. | Inspect the conflicted file. | The workspace identifies the operation and navigates conflicts with text-backed base, ours, theirs, and working-result states; missing and binary sides remain explicit. | `git ls-files -u -z` supplies stage 1/base, stage 2/ours, and stage 3/theirs records; operation metadata is read from Git's in-progress state. |
| CONFLICT-02 | approved design | A conflicted text path has a current index and working-tree fingerprint. | Choose ours, choose theirs, or edit the result. | The selected resolution is written only for the reviewed path and the UI reports the resulting unresolved/resolved state. | Accept operations use Git's stage-aware checkout followed by an index update; edited UTF-8 content is bounded and written to the working tree. |
| CONFLICT-03 | approved design | A user has produced a valid working result for a conflict. | Mark the path resolved. | The path leaves the unresolved group only after an explicit mark-resolved action; no implicit resolution is inferred from editing. | `git add -- <path>` marks a file result resolved, while a chosen deletion uses `git rm -- <path>`; the refreshed index is returned. |
| CONFLICT-04 | approved design | The index or worktree changed after the conflict view was loaded. | Apply an earlier resolution. | The mutation is rejected with a stale-resolution explanation and the current conflict remains recoverable. | Every resolution request carries a repository/path fingerprint derived from unmerged index records and the working result; Git is not invoked when it no longer matches. |
| CONFLICT-05 | approved design | All paths are resolved during an in-progress merge, rebase, or cherry-pick. | Continue or abort the reviewed operation. | Continue is enabled only with no unresolved paths; abort is always an explicit recovery action; failures retain typed operation state. | `git merge/rebase/cherry-pick --continue` or `--abort` is selected from detected metadata, and no generic failure is translated into a guessed recovery command. |
| CONFLICT-06 | approved design | A conflict is add/add, modify/delete, rename-related, or binary. | Understand which sides can be selected. | Each pane exposes available/missing/binary labels independent of color, and unavailable text cannot be edited as if it were content. | Missing stages are represented from absent index records, binary/oversized blobs return bounded state, and only supported text results can be edited. |
| STASH-01 | approved design | The repository may contain zero or more stashes. | Browse and identify a stash before applying or dropping it. | The UI lists stable stash object IDs, creation time, branch/message context, and an explicit empty state; display order is not the mutation identity. | `git stash list` supplies each stash commit OID and bounded metadata; later actions resolve the selected OID against a fresh snapshot. |
| STASH-02 | approved design | A working tree has local changes or a stash contains staged state. | Create, apply, pop, or branch from a reviewed stash. | The UI reports clean success, conflict state, or unchanged stash after a failed pop; branch-from-stash names are validated before mutation. | `git stash push`, `git stash apply`, `git stash pop`, or `git stash branch` runs against the selected stash OID and returns refreshed status/stash state. |
| STASH-03 | approved design | A stash list changed after a destructive preview. | Drop a stash without deleting a different entry. | The confirmation names the stash identity and is rejected when the selected OID or snapshot fingerprint changed. | A short-lived preview binds repository, stash commit OID, and stash-list fingerprint before `git stash drop` resolves the current reflog selector. |

| TAG-02 | approved design | A tag exists and may be pushed to a configured remote. | Delete a tag or explicitly publish it. | Deletion requires a named confirmation; push controls identify the exact tag and remote rather than pushing all tags. | `git tag --delete <name>` is preview-bound; explicit publication uses `git push <remote> refs/tags/<name>`. |
| REMOTE-02 | approved design | A remote may be added, renamed, edited, removed, or contain prunable tracking refs. | Manage remote configuration safely. | URLs are credential-safe in the UI; remove/prune previews list the remote and affected refs, and stale previews are rejected. | `git remote add/rename/set-url/remove` changes only the named remote; `git remote prune --dry-run` previews and `git remote prune` applies the reviewed cleanup. |
| UPSTREAM-01 | approved design | The current branch may have no upstream or may be ahead/behind one. | Set, unset, or publish the branch upstream. | The UI shows the selected remote/branch and refreshed ahead/behind counts; detached HEAD and missing remote states are explicit. | `git branch --set-upstream-to`, `git branch --unset-upstream`, or `git push --set-upstream` updates tracking metadata and returns status. |

## Observation protocol

For every new JetBrains behavior, record the following in order:

1. Define the repository state and the selected user intent.
2. Observe the visible controls, grouping, selection, feedback, and recovery
   path without inspecting proprietary implementation artifacts.
3. Reproduce the starting state in an isolated Git fixture.
4. Express the result as a Dart backend contract, controller state, and Flutter
   acceptance test.
5. Add a versioned note when the behavior is confirmed, changed, or still
   uncertain.

## MVP equivalence boundary

“Equivalent” means that a user can complete the same Git workflow, understand
the same important state transitions, and recover from the same failure class.
It does not mean copying source code, private protocols, exact assets, or
unnecessary visual details. gift's UI must keep its own minimal 2D pixel-game
visual language while preserving the observed workflow semantics.
